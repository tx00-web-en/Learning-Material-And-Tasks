# Pair Programming Session 2 — Tour API

In this pair programming session, you will build a **Tour API** using Node.js and Express.

This activity builds on the skills from Pair Programming Session 1. You will use the same general architecture, but this time you will work with a different data model and introduce a new development tool: **Nodemon**.

You will continue to practise:

* pair programming;
* working as Driver and Navigator;
* building REST API endpoints;
* separating routes, handlers, and application logic;
* testing APIs with Postman;
* using Git with small commits;
* writing meaningful commit messages.

You will also learn how **Nodemon** makes development faster by automatically restarting your server when your code changes.

The activity follows the same general principles used to create the [Pets API](https://github.com/tx00-resources-en/api-pets).

# 2. The Tour API

You will build an API for storing information about tours.

A tour object has the following structure:

```json
{
  "id": 1,
  "name": "Best of Paris in 7 Days Tour",
  "info": "Paris is synonymous with the finest things that culture can offer — in art, fashion, food, literature, and ideas. On this tour, your Paris-savvy Rick Steves guide will immerse you in the very best of the City of Light.",
  "image": "https://www.course-api.com/images/tours/tour-1.jpeg",
  "price": "1,995",
  "location": "Paris, France"
}
```

The `id` is generated by the application.

For this exercise, **do not use a database**. Store the tours in memory using an array.

---

# 3. API Specification

Your API will provide these endpoints:

| Method   | Path             | Purpose                 |
| -------- | ---------------- | ----------------------- |
| `GET`    | `/tours`         | Get all tours           |
| `POST`   | `/tours`         | Create a new tour       |
| `GET`    | `/tours/:tourId` | Get one tour            |
| `PATCH`  | `/tours/:tourId` | Partially update a tour |
| `DELETE` | `/tours/:tourId` | Delete a tour           |

Notice that the update endpoint uses **PATCH**, not PUT.

You will learn why later in this activity.

# 7. Pair GitHub Workflow

You will also use GitHub to collaborate on the same project.

Work with **one shared repository per pair**.

## First time: create and clone the repository

### Member 1

Member 1 creates the GitHub repository and adds Member 2 as a collaborator.

Then Member 1 pushes the initial project:

```bash
git add .
git commit -m "chore: initialize tour API"
git push -u origin main
```

### Member 2

Member 2 does **not** create a second repository.

For the first time, Member 2 clones the shared repository:

```bash
git clone <repository-url>
cd tour-api
npm install
```

After this, both partners have a local copy of the same repository.

## Before every iteration

Before starting an iteration, the partner who is about to work should make sure they have the latest version:

```bash
git pull
```

Then switch to the correct Driver/Navigator roles.

## After every iteration

The Driver:

1. finishes the iteration;
2. tests it;
3. reviews the changes with the Navigator;
4. commits the work;
5. pushes the commit.

For example:

```bash
git add .
git commit -m "feat(tours): add tour creation"
git push
```

The other partner then pulls the changes:

```bash
git pull
```

Only after pulling should they start their iteration.

## The collaboration cycle

```text
Member 1                         Member 2

work on iteration 0
commit + push
              ────────────────►  git pull

                                 work on iteration 1
                                 commit + push
              ◄────────────────
git pull

work on iteration 2
commit + push
              ────────────────►  git pull
                                 ...
```

### Important rule

Do **not** both edit and push the same iteration at the same time.

The purpose of this workflow is to practise working on a shared repository, pulling your partner's changes, and continuing from the latest version.

## Driver/Navigator and Git

The roles and Git workflow work together:

```text
Pull latest changes
       ↓
Choose Driver + Navigator
       ↓
Driver implements
       ↓
Navigator reviews and tests
       ↓
Both review the work
       ↓
Commit
       ↓
Push
       ↓
Partner pulls
       ↓
Switch roles
```

We will use the Conventional Commits style.

Some common prefixes are:

### `feat`

Use when you add functionality.

```text

```

### `fix`

Use when you correct a bug.


### `chore`

Use for maintenance or development setup.

```text
chore: install nodemon
```

### `refactor`

Use when you improve the structure of existing code without changing its behavior.


You do not need to memorize every possible commit type. For this activity, focus mainly on `feat`, `fix`, `chore`, and `refactor`.

# Iteration 1 — Install and Understand Nodemon

## Goal

Learn how Nodemon improves the development workflow.

## What is Nodemon?

Normally, when you run:

```bash
npm start
```

Node starts your application.

If you change your code, Node **does not automatically restart the server**.

You would have to stop the server and start it again.

For example:

```text
change code
   ↓
stop server
   ↓
npm start
   ↓
test again
```

This becomes annoying when you are making many small changes.

**Nodemon watches your project files.**

When it detects a relevant change, it automatically restarts the Node.js application.

The workflow becomes:

```text
change code
   ↓
Nodemon detects change
   ↓
server restarts automatically
   ↓
test again
```

This makes development much faster.

---

## Install Nodemon

Install it as a development dependency:

```bash
npm install nodemon -D
```

The `-D` means that Nodemon is installed as a **development dependency**.

Nodemon is a tool we need while developing the application. It is not part of the API itself.

---

## Add the development script

Update `package.json`:

```json
"scripts": {
  "start": "node app.js",
  "dev": "nodemon app.js"
}
```

You now have two ways to start the server.

### Normal mode

```bash
npm start
```

This runs:

```text
node app.js
```

### Development mode

```bash
npm run dev
```

This runs:

```text
nodemon app.js
```

---

## Test Nodemon

Run:

```bash
npm run dev
```

You should see Nodemon start your application.

Now make a small change to the message printed by your server.

Save the file.

Watch the terminal.

You should see Nodemon detect the change and restart the application automatically.

You **should not need to stop and manually restart the server**.

## Checkpoint

Make sure both partners can explain:

> What problem does Nodemon solve?

A good answer is:

> Nodemon automatically restarts the Node.js application when files change, making development and testing faster.

# 17. PATCH vs PUT

In this activity, we use:

```text
PATCH /tours/:tourId
```

because we want to update only part of a tour.

## PATCH — Partial Update

Suppose the existing tour is:

```json
{
  "id": 1,
  "name": "Best of Paris in 7 Days Tour",
  "info": "Explore Paris.",
  "image": "https://example.com/paris.jpg",
  "price": "1,995",
  "location": "Paris, France"
}
```

We only want to change the price.

With PATCH:

```http
PATCH /tours/1
```

```json
{
  "price": "2,095"
}
```

The result is:

```json
{
  "id": 1,
  "name": "Best of Paris in 7 Days Tour",
  "info": "Explore Paris.",
  "image": "https://example.com/paris.jpg",
  "price": "2,095",
  "location": "Paris, France"
}
```

Only the supplied field changes.

A simple way to remember it:

```text
PATCH = change part of a resource
```

# 18. What Would PUT Look Like?

`PUT` is generally used when the client sends a **complete replacement representation** of a resource.

For example:

```http
PUT /tours/1
```

The request could contain:

```json
{
  "name": "Best of Paris — Updated",
  "info": "Explore Paris and Versailles.",
  "image": "https://example.com/paris-updated.jpg",
  "price": "2,095",
  "location": "Paris, France"
}
```

The client is providing the complete representation of the tour.

Conceptually:

```text
Existing tour
     │
     ▼
    PUT
     │
     ▼
Replace with the supplied representation
```

With PATCH:

```text
Existing tour
     │
     ▼
  PATCH
     │
     ▼
Change only supplied fields
```

## Example

Starting resource:

```json
{
  "id": 1,
  "name": "Paris Tour",
  "info": "Explore Paris.",
  "image": "paris.jpg",
  "price": "1,995",
  "location": "Paris, France"
}
```

### PATCH

Request:

```http
PATCH /tours/1
```

```json
{
  "price": "2,095"
}
```

Result:

```json
{
  "id": 1,
  "name": "Paris Tour",
  "info": "Explore Paris.",
  "image": "paris.jpg",
  "price": "2,095",
  "location": "Paris, France"
}
```

The other properties remain unchanged.

### PUT

Request:

```http
PUT /tours/1
```

```json
{
  "name": "Paris Tour",
  "info": "Explore Paris.",
  "image": "paris.jpg",
  "price": "2,095",
  "location": "Paris, France"
}
```

The client sends the complete resource representation.

### Simple rule

```text
PATCH = update part of a resource

PUT   = replace the resource
```

For this activity, we use **PATCH** because our update operation is intentionally a partial update.
