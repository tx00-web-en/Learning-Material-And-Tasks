# 2. The Tour API

You will build an API for storing information about tours.

A tour object has the following structure:

```json
{
  "id": 1,
  "name": "Best of Paris in 7 Days Tour",
  "info": "Paris is synonymous with the finest things that culture can offer — in art, fashion, food, literature, and ideas. On this tour, your Paris-savvy Rick Steves guide will immerse you in the very best of the City of Light.",
  "image": "https://www.course-api.com/images/tours/tour-1.jpeg",
  "price": "1,995",
  "location": "Paris, France"
}
```

The `id` is generated by the application.

For this exercise, **do not use a database**. Store the tours in memory using an array.

---

# 3. API Specification

Your API will provide these endpoints:

| Method   | Endpoint         | Purpose                 |
| -------- | ---------------- | ----------------------- |
| `GET`    | `/tours`         | Get all tours           |
| `POST`   | `/tours`         | Create a new tour       |
| `GET`    | `/tours/:tourId` | Get one tour            |
| `PATCH`  | `/tours/:tourId` | Partially update a tour |
| `DELETE` | `/tours/:tourId` | Delete a tour           |

Notice that the update endpoint uses **PATCH**, not PUT.

You will learn why later in this activity.

# Iteration 1 — Install and Understand Nodemon

## Goal

Learn how Nodemon improves the development workflow.

## What is Nodemon?

Normally, when you run:

```bash
npm start
```

Node starts your application.

If you change your code, Node **does not automatically restart the server**.

You would have to stop the server and start it again.

For example:

```text
change code
   ↓
stop server
   ↓
npm start
   ↓
test again
```

This becomes annoying when you are making many small changes.

**Nodemon watches your project files.**

When it detects a relevant change, it automatically restarts the Node.js application.

The workflow becomes:

```text
change code
   ↓
Nodemon detects change
   ↓
server restarts automatically
   ↓
test again
```

This makes development much faster.

---

## Install Nodemon

Install it as a development dependency:

```bash
npm install nodemon -D
```

The `-D` means that Nodemon is installed as a **development dependency**.

Nodemon is a tool we need while developing the application. It is not part of the API itself.

---

## Add the development script

Update `package.json`:

```json
"scripts": {
  "start": "node app.js",
  "dev": "nodemon app.js"
}
```

You now have two ways to start the server.

### Normal mode

```bash
npm start
```

This runs:

```text
node app.js
```

### Development mode

```bash
npm run dev
```

This runs:

```text
nodemon app.js
```

---

## Test Nodemon

Run:

```bash
npm run dev
```

You should see Nodemon start your application.

Now make a small change to the message printed by your server.

Save the file.

Watch the terminal.

You should see Nodemon detect the change and restart the application automatically.

You **should not need to stop and manually restart the server**.

## Checkpoint

Make sure both partners can explain:

> What problem does Nodemon solve?

A good answer is:

> Nodemon automatically restarts the Node.js application when files change, making development and testing faster.

Initially, the handlers can return mock responses.

For example:


## Why use mock handlers?

We first want to prove that our **HTTP layer and routing work**.

Only after the routes are working will we connect the handlers to the real library functions.

This helps us isolate problems.

If a route doesn't work, we know the problem is in the routing layer rather than the business logic.

# 16. PATCH vs PUT

In this activity, we use:

```text
PATCH /tours/:tourId
```

because we want to update only part of a tour.

## PATCH — Partial Update

Suppose the existing tour is:

```json
{
  "id": 1,
  "name": "Best of Paris in 7 Days Tour",
  "info": "Explore Paris.",
  "image": "https://example.com/paris.jpg",
  "price": "1,995",
  "location": "Paris, France"
}
```

We only want to change the price.

With PATCH:

```http
PATCH /tours/1
```

```json
{
  "price": "2,095"
}
```

The result is:

```json
{
  "id": 1,
  "name": "Best of Paris in 7 Days Tour",
  "info": "Explore Paris.",
  "image": "https://example.com/paris.jpg",
  "price": "2,095",
  "location": "Paris, France"
}
```

Only the supplied field changes.

A simple way to remember it:

```text
PATCH = change part of a resource
```

---

# 17. What Would PUT Look Like?

`PUT` is generally used when the client sends a **complete replacement representation** of a resource.

For example:

```http
PUT /tours/1
```

The request could contain:

```json
{
  "name": "Best of Paris — Updated",
  "info": "Explore Paris and Versailles.",
  "image": "https://example.com/paris-updated.jpg",
  "price": "2,095",
  "location": "Paris, France"
}
```

The client is providing the complete representation of the tour.

Conceptually:

```text
Existing tour
     │
     ▼
    PUT
     │
     ▼
Replace with the supplied representation
```

With PATCH:

```text
Existing tour
     │
     ▼
  PATCH
     │
     ▼
Change only supplied fields
```

## Example

Starting resource:

```json
{
  "id": 1,
  "name": "Paris Tour",
  "info": "Explore Paris.",
  "image": "paris.jpg",
  "price": "1,995",
  "location": "Paris, France"
}
```

### PATCH

Request:

```http
PATCH /tours/1
```

```json
{
  "price": "2,095"
}
```

Result:

```json
{
  "id": 1,
  "name": "Paris Tour",
  "info": "Explore Paris.",
  "image": "paris.jpg",
  "price": "2,095",
  "location": "Paris, France"
}
```

The other properties remain unchanged.

### PUT

Request:

```http
PUT /tours/1
```

```json
{
  "name": "Paris Tour",
  "info": "Explore Paris.",
  "image": "paris.jpg",
  "price": "2,095",
  "location": "Paris, France"
}
```

The client sends the complete resource representation.

### Simple rule

```text
PATCH = update part of a resource

PUT   = replace the resource
```

For this activity, we use **PATCH** because our update operation is intentionally a partial update.
