# Pair Programming Session 1 — Feedback API

In this pair programming session, you will build a small **Feedback API** using Node.js and Express.

The goal is not only to make the API work. You will also practise:

* pair programming;
* working with a Driver and Navigator;
* designing a simple API;
* separating application layers;
* testing an API with Postman;
* making small Git commits;
* writing useful commit messages;
* reviewing your partner's code.

The activity follows the same general principles used in the [Pets API](https://github.com/tx00-resources-en/api-pets).

---

# 1. Learning Goals

By the end of this activity, you should be able to:

1. Create a basic Node.js and Express application.
2. Build REST API routes.
3. Separate routes, request handlers, and application logic.
4. Store and manipulate data in memory.
5. Implement CRUD-style API operations.
6. Test API endpoints using Postman.
7. Handle common errors such as invalid data and missing resources.
8. Work effectively using pair programming.
9. Create small, meaningful Git commits.
10. Explain the difference between `PATCH` and `PUT`.

---

# 2. The Feedback API

You will build an API for storing feedback.

A feedback object has the following structure:

```json
{
  "id": 1,
  "sender": "John Smith",
  "message": "Great session on React components! I found the examples very helpful.",
  "rating": 5,
  "platform": "mobile"
}
```

The `id` is generated by the application. The client does not need to provide it when creating feedback.

For this exercise, **do not use a database**. Store the feedback objects in memory using an array.

---

# 3. API Specification

Your API will provide the following endpoints:

| Method   | Endpoint                | Purpose                   |
| -------- | ----------------------- | ------------------------- |
| `GET`    | `/feedback`             | Get all feedback          |
| `POST`   | `/feedback`             | Create new feedback       |
| `GET`    | `/feedback/:feedbackId` | Get one feedback item     |
| `PATCH`  | `/feedback/:feedbackId` | Partially update feedback |
| `DELETE` | `/feedback/:feedbackId` | Delete feedback           |

You will implement these endpoints progressively during the activity.

# 4. Application Structure

By the end of the activity, your project should have a structure similar to:

```text
feedback-api/
│
├── app.js
├── feedbackHandlers.js
├── feedbackLib.js
├── package.json
└── package-lock.json
```

The responsibilities of the files are:

### `app.js`

Responsible for:

* creating the Express application;
* configuring middleware;
* defining routes;
* starting the server.

### `feedbackHandlers.js`

Responsible for:

* receiving HTTP requests;
* reading request parameters/body;
* calling functions from `feedbackLib.js`;
* sending HTTP responses and status codes.

### `feedbackLib.js`

Responsible for:

* storing feedback;
* creating feedback;
* finding feedback;
* updating feedback;
* deleting feedback.

Think about the architecture as:

```text
Postman
   │
   ▼
app.js
   │
   ▼
feedbackHandlers.js
   │
   ▼
feedbackLib.js
   │
   ▼
In-memory feedback array
```

# 5. Pair Programming Rules

You will work in pairs.

At any point, there are two roles.

## Driver

The Driver:

* controls the keyboard;
* writes the code;
* explains what they are doing;
* listens to the Navigator.

## Navigator

The Navigator:

* reads the requirements;
* thinks about the next step;
* checks the code;
* suggests test cases;
* looks for possible mistakes and edge cases;
* asks questions about the implementation.

### Important rule

The Navigator should **not take over the keyboard**.

The Driver and Navigator should communicate continuously.

# 7. Git Workflow

Git is part of the exercise.

You will make **small commits throughout the activity**, rather than one large commit at the end.

## The rule

At the end of every iteration:

1. Complete the implementation.
2. Test the implementation.
3. Review the changes together.
4. Decide on an appropriate commit message.
5. Make the commit.
6. Switch Driver and Navigator.
7. Start the next iteration.

### One commit = one idea

A commit should represent one meaningful change.

Good examples:

```text
feat(feedback): add feedback creation
```

```text
feat(feedback): list all feedback
```

```text
feat(feedback): find feedback by id
```

```text
feat(feedback): partially update feedback
```

```text
feat(feedback): delete feedback
```

Avoid commits such as:

```text
changes
```

```text
stuff
```

```text
finished
```

```text
update
```

# 14. PATCH vs PUT

You used `PATCH` for the update endpoint in this activity.

It is important to understand why.

## PATCH — Partial Update

`PATCH` is appropriate when you want to change **only some fields** of an existing resource.

Suppose the existing feedback is:

```json
{
  "id": 1,
  "sender": "John Smith",
  "message": "Great session!",
  "rating": 5,
  "platform": "mobile"
}
```

You want to change only the rating.

With `PATCH`:

```http
PATCH /feedback/1
```

```json
{
  "rating": 4
}
```

The result can be:

```json
{
  "id": 1,
  "sender": "John Smith",
  "message": "Great session!",
  "rating": 4,
  "platform": "mobile"
}
```

The other fields remain unchanged.

---

## PUT — Replace the Resource

`PUT` is generally used when the client sends a **complete replacement representation** of the resource.

For example:

```http
PUT /feedback/1
```

```json
{
  "sender": "John Smith",
  "message": "The session was useful.",
  "rating": 4,
  "platform": "tablet"
}
```

The server treats this as the new representation of feedback `1`.

Conceptually:

```text
Existing resource
       ↓
     PUT
       ↓
Replace with the supplied representation
```

Whereas:

```text
Existing resource
       ↓
    PATCH
       ↓
Change only the supplied fields
```

### Simple rule to remember

```text
PATCH = change part of a resource

PUT   = replace the resource
```

### Example comparison

Starting resource:

```json
{
  "id": 1,
  "sender": "John Smith",
  "message": "Great session!",
  "rating": 5,
  "platform": "mobile"
}
```

Using `PATCH`:

```http
PATCH /feedback/1
```

```json
{
  "rating": 4
}
```

Result:

```json
{
  "id": 1,
  "sender": "John Smith",
  "message": "Great session!",
  "rating": 4,
  "platform": "mobile"
}
```

Using `PUT`:

```http
PUT /feedback/1
```

```json
{
  "sender": "John Smith",
  "message": "Great session!",
  "rating": 4,
  "platform": "mobile"
}
```

The client supplies the complete resource representation.

For this activity, we use **PATCH** because the example update is intentionally a partial update.
